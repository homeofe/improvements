# Grounded Reflection Rules

> Status: v1.0 (active, adopted 2026-07-14). This rule is live.
> Purpose: define how AAHP-based workflows track provenance, require external
> grounding, and constrain self-verification so that plausibility is not mistaken
> for truth.
> This rule EXTENDS existing AAHP machinery; it does not fork or replace it. Where
> an existing mechanism already covers something (Trust Decay, the TRUST.md
> register, Phase 4 review, the verify-handoff gate), this rule references it
> rather than restating it.

## 1. Core Rule

No important claim may be treated as `verified` unless its verification basis is
explicit. A claim must not move from provenance `model_claim` (status `untested`)
to status `verified` solely because a model asserts it is correct. Verification
requires an external anchor (see section 6), recorded as provenance on the claim.

## 2. Two Axes of a Claim

Every recorded claim carries two orthogonal properties. Do not collapse them into
one list.

### Axis A - Status (grounding confidence). Reused, not new.

The only status vocabulary is `verified`, `assumed`, `untested`. This is the same
register defined by `.ai/handoff/TRUST.md`; this rule does not add levels.

- In `STATUS.md` these render inline as `(Verified)`, `(Assumed)`, `(Unknown)`.
  Register `untested` and STATUS.md `(Unknown)` are the same level.
- Grounding shorthand is a set of named points on this SAME axis, not new levels:
  - `grounded` == status `verified` (at least one external anchor confirms it)
  - `partially_grounded` == status `assumed` (cross-model reviewed or weak
    evidence; no external anchor yet)
  - `ungrounded` == status `untested` (model-only; nothing has checked it)
- Lifecycle markers are orthogonal to the three levels and are NOT provenance
  values. They are applied by the existing Trust Decay rule in
  `.claude/rules/aahp-protocol.md`:
  - `expired` - TTL lapsed; auto-downgrades `verified` to `assumed`.
  - `rejected` - claim withdrawn; never reuse.
- Do NOT build a status list that contains verification tokens (`tool_verified`,
  `source_verified`, and the like). Those are provenance values (Axis B). The status
  value for "not checked" is `untested`, and the matching provenance is `model_claim`
  (see Axis B). Do not invent a combined "generated by a model" status token.

### Axis B - Provenance (how a claim was produced or checked). New, orthogonal field.

Provenance records how a claim was produced or checked. It is a SEPARATE
field/column (for example `provenance:`), never mixed into a status list. The only
provenance vocabulary, weakest to strongest:

`model_claim` < `self_reviewed` < `cross_model_reviewed` < `source_verified` <
`tool_verified` < `test_verified` < `runtime_observed` < `human_confirmed`.

- `self_reviewed` is never final verification for high-impact work (see section 5).
- `cross_model_reviewed` is provenance only; it maps to status `assumed`, NOT
  `verified`. Consensus among models is not grounding.
- Only `source_verified`, `tool_verified`, `test_verified`, `runtime_observed`, or
  `human_confirmed` can support status `verified` (== grounded).
- The single token for "a model produced it and nothing checked it" is
  `model_claim`, which corresponds to status `untested`. Do not substitute any other
  "model-generated" label for it.

### Axis crosswalk

Use this mapping wherever grounding terms, status, and provenance meet.

| Grounding term | Status (register) | STATUS.md tag | Typical provenance |
|---|---|---|---|
| grounded | verified | (Verified) | test_verified / tool_verified / source_verified / runtime_observed / human_confirmed |
| partially_grounded | assumed | (Assumed) | cross_model_reviewed / self_reviewed |
| ungrounded | untested | (Unknown) | model_claim |

## 3. Provenance Strength (weakest to strongest)

1. `model_claim`
2. `self_reviewed`
3. `cross_model_reviewed`
4. `source_verified`
5. `tool_verified`
6. `test_verified`
7. `runtime_observed`
8. `human_confirmed`

Notes:

- Cross-model review improves robustness but does not equal truth.
- Same-provider review is weaker than cross-provider review.
- Deterministic tools are stronger than model consensus.
- Human confirmation is strongest for contextual, strategic, legal, business, or
  ethical decisions.

## 4. Required Distinctions

When recording work, keep these apart rather than blending them into one
statement: Observation, Inference, Assumption, Recommendation, Verification. An
inference presented as an observation, or an assumption presented as a
verification, is the failure mode this rule exists to catch.

## 5. Self-Verification Is Not Final Verification

Self-review must be labeled provenance `self_reviewed`. It cannot be used as final
verification for:

- security-sensitive changes
- financial or legal claims
- architecture decisions
- public documentation
- external communication
- production code
- compliance statements
- claims about current external facts

For high-impact tasks, review must come from a different model/provider than the
generator. That cross-provider second opinion is already defined as Phase 4 in
`.ai/handoff/WORKFLOW.md`, performed by `.claude/agents/reviewer.md`, and invoked
via `/review-cycle`. Use it; do not re-introduce it as new machinery. A
cross-provider review yields provenance `cross_model_reviewed` (status `assumed`),
not status `verified`.

## 6. Grounding Requirement

A claim may be recorded as `grounded` (status `verified`) only when at least one
external anchor is present:

- passing tests
- passing build
- passing type-check
- passing lint / static analysis
- schema validation
- a verified external source
- runtime observation
- a deterministic calculation
- human domain-owner confirmation

If no anchor is present, record one of:

- status `untested` / provenance `model_claim` (nothing has checked it), or
- status `assumed` / provenance `cross_model_reviewed` (partially grounded; review
  only, no external anchor yet).

The deterministic mechanical checks (MANIFEST checksum integrity, content-drift,
commit-pointer freshness, TRUST-TTL expiry) are owned by
`scripts/verify-handoff.sh`. This rule reasons on top of that gate about whether
recorded claims are actually grounded; it does not restate or replace those
mechanical checks.

### Provenance invalidation (downgrade)

Provenance can move down, not only up. If the external anchor that supported a
`verified` (grounded) claim is removed, retracted, deprecated, or found to be
incorrect, the claim reverts: to `assumed` if an independent cross-provider review
still stands (provenance `cross_model_reviewed`), otherwise to `untested`
(provenance `model_claim`). Update the affected row in `.ai/handoff/TRUST.md` when
this happens. This is distinct from TTL expiry (handled by the Trust Decay rule):
expiry is about age; invalidation is about the anchor no longer being valid.

## 7. Confidence Must Include a Source

Do not record a confidence number without the reason for it.

- Insufficient: `confidence: 0.92`
- Sufficient: `confidence: 0.92` with `confidence_source: "unit tests pass, schema
  valid, reviewed by a different provider"`

If confidence rests mainly on model judgment, say so explicitly, for example
`confidence_source: model_reasoning_only`, and keep the status at `untested` or
`assumed`. Confidence-band guidance lives in `.ai/GROUNDING.md`; use it rather than
inventing local bands.

## 8. Required Reflection Questions

Before handoff, and whenever an output is high-impact, answer:

1. What assumptions does this output rely on?
2. Which claims are `verified`, which are `assumed`, and which are `untested`?
3. What evidence or observation would make the conclusion false?
4. What is the strongest counterargument that this output is wrong?
5. Which claims still need an external grounding anchor?
6. What remains uncertain, and how much does that uncertainty matter?
7. What should the next agent verify first?
8. Did any claim reach status `verified` without a provenance anchor from section 6?

## 9. Challenge Trigger

Run an adversarial challenge (the `/challenge` command) when the output:

- is important or stated with high confidence
- affects architecture or a design decision
- will be shown externally or published
- touches security, compliance, legal, financial, or governance concerns
- was generated and reviewed by the same model (circular reasoning risk)
- depends on current external facts that may have changed

A challenge reverses the burden of proof: instead of "Is this correct?", ask "What
is the strongest reason this could be wrong?" It surfaces hidden assumptions,
failure modes, and provenance gaps, and recalibrates confidence.

## 10. Audit Trigger

The grounding auditor is an on-demand agent, invoked like `/review-cycle`. It MAY
also run as an optional pre-handoff check for high-impact tasks, labelled "Phase
4.5 (optional, pre-handoff)", before the terminal Phase 5 Handoff. It is never
"Phase 6": Phase 5 is the final atomic step where `MANIFEST.json` is regenerated
and the branch is pushed, so an audit placed after it could not gate the commit.

Invoke the auditor when:

- a high-impact task is about to hand off
- provenance is missing on claims marked `verified`
- the same model appears to have generated and approved a claim (circular review)
- a critical trust record has `expired`
- confidence is high but no tool, test, or source anchor is recorded

Scope is grounding and trust-of-claims only: are STATUS.md and TRUST.md assertions
actually grounded, are there provenance gaps, is there circular review, is any
trust expired. It is NOT code review; code review is Phase 4 (reviewer.md +
`/review-cycle`) plus the deterministic `scripts/verify-handoff.sh` gate. The
auditor emits one verdict: `SHIP`, `NEEDS_CHANGES`, or `BLOCK` (the same verdict
vocabulary as `.claude/agents/reviewer.md`). Do not introduce other verdict names.

## 11. AAHP Handoff: Grounded Reflection Section

Every handoff must include a "Grounded Reflection" section. Each listed claim
should carry its status and provenance, and be recorded as a row in
`.ai/handoff/TRUST.md`:

- Verified Claims - status `verified`; list the provenance anchor for each.
- Assumed Claims - status `assumed`; typically `cross_model_reviewed` or
  `self_reviewed` (partially grounded).
- Untested Claims - status `untested`; provenance `model_claim`; nothing has
  checked them yet.
- Assumptions - working assumptions the output depends on.
- Counterarguments - the strongest reasons the output could be wrong.
- Required External Checks - anchors still needed to move claims to `verified`.
- Residual Risk - what remains uncertain and how much it matters.

TTLs and expiry for these records are governed by the Trust Decay rule in
`.claude/rules/aahp-protocol.md` and the per-row TTL / Expires columns in
`.ai/handoff/TRUST.md`. Do not define new day-tier TTL tables here.

## 12. Do-Not-Overclaim Rule

Agents must not state "This is correct", "This is safe", "This is compliant",
"This is production-ready", or "This is true" unless the claim is verified or
reviewed to the level required in section 5. Prefer calibrated language:

- "This appears consistent with ..."
- "This is model-reviewed but not externally verified."
- "This is partially grounded by ..."
- "This requires human or domain verification before use."
